# Минимальный LLM-сервис

Сервис принимает текст, кратко суммаризирует его через OpenAI-совместимую модель и возвращает JSON. Запрос проходит по слоям: проверка ввода, сценарий, промпт, кеш, вызов модели, очистка ответа.

## Архитектура

```
my_llm_service/
├── api/            # POST /chat, коды ошибок
├── services/       # сценарий суммаризации
├── llm/            # промпт, HTTP-клиент, разбор ответа
├── cache/          # ключ и словарь с TTL
├── config/         # YAML и JSON-логи
├── tests/          # автотесты и локальная заглушка модели
├── main.py
├── requirements.txt
└── README.md
```

Цепочка одного запроса:

1. `POST /chat` принимает JSON с полем `message`.
2. API проверяет тип, пустоту и длину (не больше 1000 символов).
3. Бизнес-логика выбирает сценарий `summarize`.
4. Prompt builder собирает системную инструкцию и пользовательский текст.
5. Кеш ищет готовый результат. Ключ — SHA-256 от текста, модели, температуры, `max_tokens` и системного промпта.
6. При промахе клиент вызывает `POST {base_url}/chat/completions` с таймаутом 15 секунд.
7. Временные сбои (таймаут, обрыв сети, HTTP 408, 429, 5xx) повторяются до 3 попыток. Паузы 0,5 с и 1 с.
8. Ответ модели должен быть JSON `{"summary": "..."}`. Лишние пробелы убираются, markdown-ограда вокруг JSON снимается.
9. Успешный результат кладётся в кеш на 10 минут. Ошибки в кеш не пишутся.

## Требования

- Python 3.9 или новее
- Доступ к OpenAI-совместимому API, если нужен живой вызов модели

Зависимости перечислены в `requirements.txt`: Flask, requests, python-dotenv, PyYAML, pytest. Там же зафиксирован `urllib3==1.26.20`: стандартный Python 3.9 на macOS собран с LibreSSL, и вторая версия urllib3 при импорте печатает предупреждение.

## Установка и запуск

```bash
cd my_llm_service
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Откройте `.env` и укажите ключ:

```
LLM_API_KEY=ваш_ключ
```

При необходимости раскомментируйте адрес и модель. Для Ollama, например:

```
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=llama3.2
LLM_API_KEY=ollama
```

Запуск:

```bash
python main.py
```

Сервис слушает `http://127.0.0.1:8000`. Проверка живости: `GET /health`.

Пустой ключ не мешает старту. Вызов модели в этом случае сразу возвращает fallback и в сеть не ходит.

## Примеры запросов и ответов

Успешная суммаризация:

```bash
curl -s -X POST http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"message": "Python — язык с динамической типизацией. Его часто используют для веб-сервисов и автоматизации."}'
```

```json
{
  "scenario": "summarize",
  "summary": "Python — динамически типизированный язык, который часто применяют для веб-сервисов и автоматизации.",
  "cached": false
}
```

Формулировка `summary` зависит от модели. Поле `cached` равно `true`, если ответ взят из кеша.

Повтор того же текста с теми же параметрами модели и тем же системным промптом не вызывает модель ещё раз. В логе будет событие `cache_hit`.

Нет поля `message`:

```bash
curl -s -X POST http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{}'
```

```json
{"error": "Поле message обязательно."}
```

Статус 400. Та же ошибка для пустой строки и строки из пробелов. Слишком длинный текст:

```json
{"error": "Поле message не должно превышать 1000 символов."}
```

Модель недоступна, сеть оборвана или ключ не задан:

```json
{"error": "Сервис временно недоступен, попробуйте позже"}
```

Статус 503. Процесс при этом продолжает работать. Такой ответ не кешируется: следующий запрос снова идёт в модель.

Модель вернула текст, который не является JSON `{"summary": "..."}`:

```json
{"error": "Не удалось обработать ответ модели. Попробуйте ещё раз."}
```

Статус 502.

## Кеш, ретраи, fallback

- Кеш хранится в памяти процесса. После перезапуска он пуст.
- TTL по умолчанию — 600 секунд (`config/settings.yaml`, секция `cache`).
- В ключ входят текст запроса, `model`, `temperature`, `max_tokens` и системный промпт. Смена любого из них даёт промах.
- Повтор делается только для временных ошибок. Ответ 4xx (кроме 408 и 429) не повторяется.
- После исчерпания попыток клиент получает fallback и статус 503. В текст ошибки не попадают детали сети и ключ.

## Логи

Каждая прикладная запись — одна строка JSON. Она пишется в консоль и в `logs/service.log`.

В журнале есть входящий запрос, результат валидации, выбранный сценарий, собранный промпт, `cache_hit` или `cache_miss`, вызов модели, число попыток, ответ модели, итог очистки и общее время запроса. У каждого этапа есть `elapsed_ms`, где это уместно. Заголовок `Authorization` в лог не попадает.

Пример:

```json
{"timestamp": "2026-11-12T07:00:00.000000+00:00", "level": "INFO", "logger": "my_llm_service", "event": "cache_hit", "request_id": "a1b2c3d4e5f6", "cache_key": "…", "elapsed_ms": 0.12, "ttl_seconds": 600}
```

## Тесты

```bash
pytest -q
```

Автотесты не ходят в сеть: HTTP-клиент подменяется. Они проверяют валидацию, кеш, TTL, состав ключа, таймаут в запросе, три попытки с паузами 0,5 и 1 с, отказ от ретрая на HTTP 400 и fallback при обрыве соединения.

## Чек-лист ручной проверки

- Корректный `POST /chat` с непустым `message` короче или равным 1000 символам возвращает 200, сценарий `summarize` и непустой `summary`. В логе есть `cache_miss`.
- Повтор того же JSON возвращает тот же `summary` и `"cached": true`. В логе есть `cache_hit`, нового `llm_request` нет.
- Запрос без поля `message` возвращает 400 и текст «Поле message обязательно.»
- Пустое или пробельное `message` возвращает 400 и текст «Поле message не должно быть пустым.»
- Текст длиннее 1000 символов возвращает 400 и сообщение о лимите.
- Недоступная модель (остановленный провайдер или пустой ключ) возвращает 503 и «Сервис временно недоступен, попробуйте позже». Процесс не завершается. Повтор не берётся из кеша.
- Ответ модели, который не является нужным JSON, возвращает 502.
- В `logs/service.log` строки являются JSON и содержат этапы запроса вместе с `cache_hit` / `cache_miss`.

### Проверка без внешнего ключа

В одном терминале поднимите заглушку. `STUB_FAIL_FIRST=2` заставляет её дважды ответить HTTP 500, чтобы на первом запросе были видны ретраи:

```bash
STUB_FAIL_FIRST=2 python tests/manual_stub.py
```

В другом:

```bash
LLM_BASE_URL=http://127.0.0.1:9999/v1 LLM_API_KEY=test-key python main.py
```

Дальше выполните пункты чек-листа через `curl`. Маркер `__bad_json__` внутри текста понимает только заглушка: она специально возвращает не-JSON, чтобы проверить статус 502. Остановите заглушку и отправьте новый текст — сервис должен вернуть fallback. Уже закешированный текст по-прежнему отдаётся из памяти.

Результаты прогона лежат в `test_report.md`.
